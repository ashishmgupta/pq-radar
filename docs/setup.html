Setup guide

Clone and deploy PQ Radar to a company Cloudflare account

One tab per step, in order. Commands are PowerShell (Windows). Anything highlighted like this is a placeholder in the code or config that you must replace with your own value. Real values go in a local, gitignored config file — never in the repo.

Overview & checklist

PQ Radar is a Cloudflare Worker (UI + API), a D1 database, and a Python probe container that runs the TLS/SSH/FTPS handshakes. Setup is about 30–45 minutes once you have the access below.

Two kinds of Cloudflare account — don't conflate them

RoleWhat it doesConfig it drives
Hosting accountWhere the Worker, D1 database, Durable Object and container image live. wrangler deploy acts here.Your Wrangler login / setup token. Optional account_id in the local config.
Scanned account(s)Whose zones and DNS records are read to build the hostname → origin map. Read-only. Can be the same account or different ones.CF_ACCOUNT_ID, CF_ACCOUNT_ID_QA (vars) plus CF_API_TOKEN, CF_API_TOKEN_QA (secrets).

The path

  1. Permissions — confirm every access, plan and approval first (next tab). Most delays happen here.
  2. Clone & install the repo.
  3. Authenticate Wrangler to the hosting account.
  4. Config — create wrangler.local.jsonc and fill every placeholder.
  5. D1 — create the database, apply the schema.
  6. Deploy the Worker and container.
  7. Secrets — the read-only scan tokens.
  8. Access — put Cloudflare Access in front of the UI.
  9. First run — pull zones, scan, verify.
Why deploy before secrets: secrets attach to an existing Worker, and the first deploy also builds the container (the slow part). Doing it in this order means you hit any Docker or plan problem before you've handled any tokens.

Permissions & prerequisites

Everything you need before touching a command. Permission names are as the Cloudflare dashboard labels them at the time of writing; labels shift slightly, but the capability is what matters.

A. Your Cloudflare user (dashboard)

NeedWhy
Member of the hosting account with rights to create Workers and D1 databasesDeploy the Worker, create the database. An Administrator or a role with Workers + D1 edit works.required
Zero Trust enabled on that account, and a role that can edit Access applications and policiesCreate the Access application and copy its AUD tag. Creating a Zero Trust organization (team name) is a one-time step if it doesn't exist. Free plan covers up to 50 users.required for Access
Read access to the zones/DNS on each scanned accountNeeded to create the scan token and confirm the account IDs.required

B. Plan

  • Workers Paid plan on the hosting account. The probe runs on Cloudflare Containers, which (to my knowledge) is not available on the free Workers plan. Confirm this with whoever owns the account before starting.
  • D1 and the Zero Trust free tier need nothing extra for this app.

C. Setup token — what wrangler itself acts as

Used a handful of times to provision. A scoped token is safer than full admin and easier to get approved. Create it under My Profile → API Tokens (or Account API Tokens), scoped to the hosting account. Alternatively use npx wrangler login if OAuth for CLIs is allowed.

PermissionScopeWhy
Workers Scripts — EditAccountDeploy the Worker
D1 — EditAccountCreate the database, apply the schema
Workers Cloudflare Containers — EditAccountBuild and push the probe container image
Account Settings — ReadAccountLets Wrangler identify the account non-interactively
Workers Routes — EditZoneonly if you attach a custom domain

D. Scan token(s) — one per scanned account

Read-only and long-lived; stored as a Worker secret. If one leaks, the worst case is someone learns your DNS records. Account-wide scope is deliberate, so adding a zone later needs no token edit.

PermissionScopeWhy
Zone — ReadAll zones on that accountEnumerate which zones exist
DNS — ReadAll zones on that accountRead the records that build hostname → origin

E. This laptop

  • Git, and Node.js (current LTS) with npm.
  • Docker Desktop, running — wrangler deploy builds the container image locally and pushes it. Without Docker the Worker can deploy but the probe cannot, so scans will not work.
  • Outbound HTTPS to api.cloudflare.com, registry.cloudflare.com, the npm registry and Docker Hub. Behind a TLS-inspecting proxy you may need NODE_EXTRA_CA_CERTS pointing at the corporate root CA, and the same CA trusted by Docker.
  • PowerShell. Commands below use $env:NAME = "..." syntax and curl.exe (not the PowerShell curl alias).

F. Approvals and network, not Cloudflare permissions

  • Tell the security team. Scans open real TLS connections to your own origins; a continuous schedule can trip monitoring or read as probing. The default cron is once a day.
  • Origin firewalls must accept connections from Cloudflare's container egress, and only publicly reachable origins can be scanned — private (RFC 1918) addresses are out of reach.
  • workers.dev may be blocked by company policy. A custom domain means a DNS record on a shared zone, which usually needs someone else's sign-off.
  • Confirm you are allowed to run this scanner against the target accounts.

Clone & install

The public repo ships with no real IDs, zones or secrets, so a fresh clone is safe to work in.

powershell
git clone https://github.com/ashishmgupta/pq-radar.git
cd pq-radar
npm install
node --version   # confirm Node is installed
docker --version # confirm Docker is installed; Docker Desktop must also be running
The repo is public. Never commit real account IDs, the database ID, Access values or tokens. Step 4 puts them in wrangler.local.jsonc, which is already in .gitignore. Before any commit, run git status and read the list.

Authenticate Wrangler

Point Wrangler at the hosting account. On a company account, prefer the scoped setup token from the Permissions tab — no OAuth popup, and it sidesteps policies that block third-party OAuth for CLIs.

powershell — setup token (preferred)
$env:CLOUDFLARE_API_TOKEN  = "YOUR-SETUP-TOKEN"
$env:CLOUDFLARE_ACCOUNT_ID = "HOSTING-ACCOUNT-ID"
npx wrangler whoami
powershell — or browser login
npx wrangler login
npx wrangler whoami
  • whoami must list the hosting account and the permissions from the setup token. If it shows the wrong account, fix it now — a deploy to the wrong account is the costliest mistake in this guide.
  • Environment variables last for this PowerShell session only. Re-export them in any new window.
  • Where to find an account ID: dashboard → Account home → the “⋯” menu next to the account → Copy account ID; or the right sidebar of any zone's Overview page.
Don't paste tokens into chat, tickets or files in the repo. The setup token is only ever set as an environment variable.

Config & placeholders

The tracked wrangler.jsonc contains placeholders. Copy it to a local, gitignored file and fill those in there — the real values never touch the repo.

powershell
Copy-Item wrangler.jsonc wrangler.local.jsonc
git check-ignore wrangler.local.jsonc   # must print the filename; if blank, STOP
git status                              # wrangler.local.jsonc must NOT be listed

Placeholders to replace in wrangler.local.jsonc

What it should look like

wrangler.local.jsonc — relevant parts
{
  "name": "pq-radar",
  "main": "src/index.ts",
  "account_id": "HOSTING-ACCOUNT-ID",          // optional, recommended
  "vars": {
    "CF_ACCOUNT_ID": "SCANNED-ACCOUNT-ID",
    "CF_ACCOUNT_ID_QA": "SECOND-SCANNED-ACCOUNT-ID"   // delete if only one
    // Added in step 8:
    // "ACCESS_TEAM_DOMAIN": "...", "ACCESS_AUD": "..."
  },
  "d1_databases": [
    { "binding": "DB", "database_name": "pq-radar",
      "database_id": "D1-DATABASE-ID" }
  ]
}

Other behavior in the file (no edit needed)

  • Cron 0 6 * * * — daily at 06:00 UTC. Raise it only after telling your security team.
  • Container max_instances: 1, built from ./container/Dockerfile; Durable Object ProbeContainer. Leave as is.

More than two scanned accounts?

Instead of the two vars, set one var CF_ACCOUNTS to a JSON array of {label, accountId} pairs, plus one secret per label named CF_API_TOKEN_<LABEL> (label uppercased, non-alphanumerics replaced by _). When set, it replaces CF_ACCOUNT_ID/_QA entirely. See the README for the exact format.

From here on, every Wrangler command ends with -c wrangler.local.jsonc. Without it Wrangler reads the placeholder file and fails or targets the wrong thing.

Create the D1 database

Needs the D1 — Edit permission. This creates an empty database and then loads the full table structure.

  1. Create it:
    powershell
    npx wrangler d1 create pq-radar -c wrangler.local.jsonc
  2. Copy the database_id from the output into wrangler.local.jsonc → d1_databases[0].database_id, replacing REPLACE_WITH_YOUR_D1_DATABASE_ID. If Wrangler offers to write the binding into a config file, make sure that is the local file, not wrangler.jsonc.
  3. Load the schema (brand-new, empty database only):
    powershell
    npx wrangler d1 execute pq-radar --remote --file=schema.sql -c wrangler.local.jsonc
  4. Check the tables exist:
    powershell
    npx wrangler d1 execute pq-radar --remote -c wrangler.local.jsonc `
  --command "SELECT name FROM sqlite_master WHERE type='table' ORDER BY name"
    You should see runs, results, zones, dns_records, subnets and others.
Run schema.sql once. Against a database that already has these tables every statement fails loudly (it will not touch your data). To upgrade an existing deployment later, use npx wrangler d1 migrations apply pq-radar --remote -c wrangler.local.jsonc instead.

Deploy the Worker and container

Needs Workers Scripts — Edit and Containers — Edit, Docker Desktop running, and the Workers Paid plan.

powershell
docker info | Select-String "Server Version"   # must print a version, else start Docker Desktop
npx wrangler deploy -c wrangler.local.jsonc
  • The first deploy builds the probe image and pushes it to Cloudflare's registry — allow several minutes.
  • On success Wrangler prints the URL, usually https://pq-radar.your-subdomain.workers.dev, and the cron schedule. Note the URL.
  • Wrangler lists the bindings it sees. Check that DB and your account-ID vars are the ones you intended.
At this point the UI is reachable but unprotected and has no scan tokens yet. It will show an empty state. Do steps 7 and 8 straight away, and don't share the URL until Access is on.
No Docker available? --containers-rollout=none deploys the Worker alone. That is fine for config changes after the container already exists, but on a first deploy there is no probe, so scans cannot run.

Scan tokens as secrets

Create one read-only scan token per scanned account (Zone — Read and DNS — Read, all zones; see Permissions), validate it, then store it as a Worker secret.

  1. Validate the token before storing it:
    powershell
    $env:SCAN_TOKEN = "SCAN-TOKEN"
curl.exe -s -H "Authorization: Bearer $env:SCAN_TOKEN" "https://api.cloudflare.com/client/v4/zones?per_page=5"
    Expect "success": true and your zones. An auth error means the token lacks Zone Read, or is scoped to the wrong account.
  2. Store it. Wrangler prompts for the value — paste it there, not on the command line:
    powershell
    npx wrangler secret put CF_API_TOKEN    -c wrangler.local.jsonc
npx wrangler secret put CF_API_TOKEN_QA -c wrangler.local.jsonc   # only if you set CF_ACCOUNT_ID_QA
  3. Confirm the names (values are never shown):
    powershell
    npx wrangler secret list -c wrangler.local.jsonc
Remove-Item Env:SCAN_TOKEN
SecretWhen
CF_API_TOKENrequired token for the account in CF_ACCOUNT_ID
CF_API_TOKEN_QAonly if CF_ACCOUNT_ID_QA is set
CF_API_TOKEN_<LABEL>one per entry when using CF_ACCOUNTS
TRIGGER_SECREToptional not needed with Access. Set it only if scripts must call the API with a Bearer token.
Never store tokens in a file in the repo folder. A scratch file with real tokens is the most common way credentials end up committed. Use a password manager.

Protect it with Cloudflare Access

This app's data is a map of every origin IP behind your CDN. Put Access in front of it: per-user sign-in, no shared password. The Worker verifies Access's signed token itself (signature, issuer, audience, expiry), so it stays safe even if its workers.dev URL is reached without going through Access. Needs a role that can edit Access applications and policies.

1. Create the application

  1. Zero Trust → Access controls → Applications → Add an application.
  2. Choose Self-hosted and private → Workers for a workers.dev URL (for a custom domain, use the Public DNS / hostname option instead). Continue.
  3. Name it pq-radar. Under Destinations, set Scope to your pq-radar Worker and Type to A Worker's production and preview URLs.
  4. Policy: action Allow; Include → Emails selector listing named people (not “Emails ending in”), or an Access Group for easy on/offboarding. Leave MFA/justification options off unless required.
  5. Login methods: your company identity provider, or one-time PIN. Save the application.

2. Collect the two values

ValueWhereLooks like
ACCESS_TEAM_DOMAINZero Trust → Settings → Custom pages → Team domainyour-team.cloudflareaccess.com (bare hostname, no https://)
ACCESS_AUDOpen the application → Additional settings tab → Application Audience (AUD) Tag (copy icon)64 hex characters
Both must come from the same account. The team domain and the application belong to one Cloudflare account; the Worker must be in the account whose Zero Trust holds that application. A mismatch makes every call return 401. The AUD is per application: a second Access app (for example for a custom domain) has a different AUD.

3. Add them to the local config and redeploy

wrangler.local.jsonc — inside "vars"
"ACCESS_TEAM_DOMAIN": "your-team.cloudflareaccess.com",
"ACCESS_AUD": "64-character-aud-tag"
powershell
npx wrangler deploy -c wrangler.local.jsonc --containers-rollout=none

--containers-rollout=none is safe here: only vars changed, so the container image does not need rebuilding (and Docker isn't required for this redeploy).

4. Verify

  • Open the URL in a fresh incognito window: you must hit the Access sign-in first, then land on the data with no secret prompt.
  • From PowerShell: curl.exe -s -o NUL -w "%{http_code}" https://pq-radar.your-subdomain.workers.dev/api/readiness should return 302 (redirect to the Access login), never 200.
  • npx wrangler secret list -c wrangler.local.jsonc should not contain TRIGGER_SECRET, unless you chose to keep it for scripts.
Skipping Access? Then set the shared secret instead (npx wrangler secret put TRIGGER_SECRET -c wrangler.local.jsonc) and the UI will ask for it. That is a single shared password with no per-user identity or audit trail — acceptable solo, thin for a shared deployment.

One-time-PIN-only sign-in proves mailbox control, not current employment; prefer your company identity provider where you can. Scheduled cron scans don't go through HTTP, so Access does not affect them.

First run & verify

  1. Open https://pq-radar.your-subdomain.workers.dev/readiness and sign in through Access.
  2. Click Pull zones from Cloudflare. This reads zones and DNS records through your scan token(s). If it returns zero zones, see Troubleshooting.
  3. Click Run full scan. The probe container starts (first start takes a moment) and works through the edge, origin, SSH and FTPS legs.
  4. Watch results fill in on /readiness. A row's detail view shows the exact openssl s_client exchange behind each verdict, and for origin IPs with no DNS record the TLS certificate names appear (lock icon), which helps match an IP to its app.

Optional: sweep your own network ranges by CIDR

Origins outside any configured range are still scanned as extras. Add a range only if you want address-by-address sweeps:

powershell
npx wrangler d1 execute pq-radar --remote -c wrangler.local.jsonc `
  --command "INSERT INTO subnets (cidr, label, enabled) VALUES ('YOUR.CIDR.HERE/24', 'label', 1)"

Optional: custom domain

Dashboard → the Worker → Settings → Domains & Routes, or a routes entry in the local config. Needs Workers Routes — Edit, the zone must be in the same account, and it adds a DNS record (get sign-off). If you do this, the Access application must cover the new hostname, and a hostname-based app has its own AUD tag: update ACCESS_AUD and redeploy.

Troubleshooting

SymptomLikely cause & fix
The Docker CLI is needed… on deployDocker Desktop isn't running. Start it and retry; first-time deploys need it to build the image.
whoami shows the wrong accountStale CLOUDFLARE_ACCOUNT_ID or an old wrangler login. Re-export the variables, or set account_id in the local config.
Deploy fails on containers or D1 permissionSetup token is missing Containers — Edit or D1 — Edit, or the plan is the free Workers plan. Re-check the Permissions tab.
npm, wrangler or Docker cert errorsTLS-inspecting proxy. Set NODE_EXTRA_CA_CERTS to the corporate root CA and trust it in Docker.
d1 execute errors on schema.sql (“already exists”)Schema was already applied. Don't re-run; use d1 migrations apply for upgrades.
Everything returns 401 after enabling AccessWrong ACCESS_TEAM_DOMAIN or ACCESS_AUD, or the application belongs to a different account/hostname. Open https://team.cloudflareaccess.com/cdn-cgi/access/certs — it should return JSON with a keys array — and re-copy the AUD from the right application.
Page shows the old secret prompt after signing inAccess session expired mid-use. Refresh the page. If it persists, one of the two Access vars is missing from the deployed Worker; redeploy.
Incognito loads the app with no Access loginThe application's destination doesn't cover this URL. Edit the application's Workers destination and Save.
workers.dev blocked on the corporate networkUse a custom domain (needs a DNS record on a zone in the same account, with sign-off).
Pull zones returns 0 zonesScan token lacks Zone — Read, is scoped to the wrong account, or CF_ACCOUNT_ID still holds the placeholder. Re-run the validation curl in the Secrets tab.
A “QA missing” warning, or a bogus second accountCF_ACCOUNT_ID_QA is still set to its placeholder. Delete the line if you scan only one account.
Origins never reach “live”Origin firewall blocks Cloudflare egress, the address is private, or the origin isn't listening on the port. Dead IPs are reported as such, not hidden.
Some subdomains missing from the scanRecords are only read from zones the token can see. A subdomain delegated by NS to another DNS zone is not followed; that target zone must itself be visible to a scanned account.
