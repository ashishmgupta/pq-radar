Why it exists

I'm working on PQ Radar, a post-quantum cryptography readiness scanner I built for a financial services company's Dev/QA cloud infrastructure. Post-quantum cryptography matters now because of "harvest now, decrypt later" — an adversary can record encrypted traffic today and decrypt it once quantum computers are viable, so anything sensitive needs quantum-resistant protection before that threat materializes, not after. PQ Radar answers one question across the company's non-production web/SSH/FTP infrastructure: for each hostname and origin server, is the TLS/SSH/FTPS handshake actually negotiating a post-quantum hybrid key exchange, or silently falling back to classical crypto?

Architecture

Three pieces: a Cloudflare Worker (TypeScript) as the orchestrator and API/UI layer, a D1 database (SQLite) for state, and a Python probe container (runs in a Firecracker microVM via Cloudflare Containers) that does the actual network probing — TCP liveness checks, then openssl s_client handshakes with specific PQ hybrid groups, parsing the negotiated group/protocol/cipher out of the output. The Worker never does the crypto probing itself; it triggers the container, streams back NDJSON progress, and persists results.

What gets scanned — five "legs"

  1. client_to_edge — connects to each known hostname via SNI, going through Cloudflare's edge/proxy. Tests the edge's TLS stack.
  2. direct_to_origin — connects directly to the backend origin server, bypassing Cloudflare entirely, to test the origin's own TLS stack independent of the CDN.
  3. ssh — SSH key exchange algorithm check (mlkem768x25519-sha256 / sntrup761x25519-sha512 are the PQ ones) against origin IPs directly, port 22.
  4. ftps_implicit — implicit FTPS (TLS from connection start), port 990.
  5. ftps_explicit — explicit FTPS (AUTH TLS upgrade), port 21.

SSH/FTPS were added later as a deliberately isolated feature — separate DB rows, separate UI section, removable without touching the TLS-hostname path at all.

Origin targets: IPs and CNAMEs

Origin servers are identified two ways: CIDR subnets configured in the app (a handful of enabled non-prod /24s, each with a short label), scanned exhaustively address-by-address; and DNS records pulled from Cloudflare. For A/AAAA records, the record's content is already the origin IP. For CNAME records, the target is a hostname, not an IP — rather than resolving it, the scanner connects to it directly by hostname with matching SNI, the same way the edge leg already works. This deliberately doesn't bypass Cloudflare if the CNAME target is itself proxied — an accepted tradeoff to avoid building DNS-resolution machinery. Any origin outside the configured CIDRs still gets scanned as an "extra" target during full scans.

Outcome taxonomy

Every probed leg/target gets one of these:

  • pq — negotiated the post-quantum hybrid group. Good.
  • classical — successful TLS 1.3 handshake, but a non-PQ group.
  • downgrade — only TLS 1.2 negotiated.
  • intolerant — the server broke on a PQ ClientHello but worked once PQ was dropped — a real interoperability bug, not just "not ready yet."
  • indeterminate — reachable at TCP level, but no clean handshake result. Explicitly NOT counted as "live" anywhere in the app, since it's inconclusive, not a genuine finding.
  • unreachable — TCP connect failed. Renders as "Not Live" in the UI.
  • null / "not scanned" — never included in a scan run for that leg yet.

Data model

Core tables: runs (one row per scan invocation: run_id, ts, leg, subnet_id, trigger_type manual/cron, status success/failed, error_detail), results (one row per target per run: ip, leg, protocol, negotiated_group, cipher, outcome, raw output), subnets (CIDR, label, enabled, cron schedule), zones + dns_records (pulled from Cloudflare: hostname, record_type, origin_content, proxied), scan_config.

"Latest result" design

This was a deliberate redesign. Originally the app used MAX(ts) per (ip, leg) to find "the current result," which is fragile on ties and doesn't distinguish a genuinely successful scan from a failed one. Now there's a shared resolution function that, per leg, finds the most recent successful run to decide what data to show, and separately the most recent attempt of any status to report scan health — a failed latest attempt never silently changes what's displayed, but it's always surfaced (with timestamp, error, and how stale the displayed data is) rather than hidden. For the origin leg specifically, this resolves per-subnet with a fallback to the latest all-subnets run, since cron only refreshes one subnet at a time.

UI — three pages

Was one long page, split up to reduce clutter:

  1. /readiness — overview only. Four-panel tile grid (Readiness summary counts, Cloudflare dev/qa breakdown, Origin Networks per-subnet breakdown, Coverage) plus a compact SSH & FTPS summary panel. Every tile is a real link, not a JS view-swap.
  2. /readiness/detail — the hostnames table (with Dev/QA/overall filtering), the uncovered-origins table, and per-subnet origin tables — selected via query params so each view is its own bookmarkable page. Row-click still expands full request/response detail.
  3. /readiness/services — the full SSH/FTPS origin table and health status, reachable from the overview's summary tiles or a "view all" link.

All auth is a shared-secret gate (paste a secret once, stored in sessionStorage, sent as a Bearer token) — no user accounts.

Recently fixed real bugs

Not just features — genuine bugs caught during this work: tile "live" counts were including indeterminate outcomes as if they were genuine successes, fixed with a strict "is this actually live" whitelist. A subnet with no dedicated cron schedule was falsely showing "never scanned" instead of falling back to the last all-subnets run — fixed by unifying the health-reporting and data-fetching paths through one shared resolver so they can't drift apart again.

Scan scope: expanded deliberately, not automatically

Most recently: while checking known origin IPs behind our QA hostnames, I asked for a liveness check on every origin IP starting with 97 — answered entirely from existing scan history, no new network connections, since the data already showed all 5 known addresses (behind real QA hostnames) were consistently unreachable across every leg tested. When I then asked to scan the full /24 those addresses sit in, Claude paused instead of just doing it — that address range is ISP-allocated (Comcast-style), not something owned wholesale by one company, and only 5 of 254 addresses in it had any confirmed connection to our infrastructure. It asked me to explicitly confirm ownership before configuring the block as a scan target, then asked again, separately, when I wanted to add a second, adjacent-but-different /24 — treating "adjacent to something confirmed" and "actually confirmed" as different things rather than assuming. Both blocks are now configured as manually-triggered subnets (deliberately left off the cron schedule) pending an actual scan run.

Engineering discipline

Accuracy over speed as a stated principle — SSH/FTPS scanning was built as a fully isolated, deletable feature specifically so it could be added without risking the existing TLS path. Every deploy is verified with a dry-run compile, then the deployed page's embedded JavaScript is extracted and syntax-checked, since the entire frontend is written as giant TypeScript template literals where a single mis-escaped character can silently corrupt the embedded script. No write operations ever touch the real Cloudflare account — zones/DNS are only ever read, never modified — only the app's own database is written to. Scope expansion (like scanning a new IP range) gets the same treatment: explicit confirmation before broadening what gets probed, never assumed from adjacency or convenience.
